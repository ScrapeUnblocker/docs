---
title: "Handling failures"
description: "What 403, 503, 504, 523, 422 and a dead URL actually mean - and how to recover from each."
---

ScrapeUnblocker tries every available bypass route before giving up. When it does return a non-2xx, the status code tells you exactly what went wrong. This guide covers the playbook for each.

## 403 - blocked on every route

We tried every bypass we have for this domain - direct, residential, stealth browser, fallback provider - and every path was blocked.

**Recovery:**

1. **Switch `proxy_country`.** This is the highest-yield fix. Many sites apply country-specific bot rules.

   ```bash
   curl -X POST "https://api.scrapeunblocker.com/getPageSource?url=...&proxy_country=de" \
     -H "x-scrapeunblocker-key: YOUR_API_KEY"
   ```

2. **Wait a few minutes and retry.** Rate-based blocks expire on their own.

3. **Lower request volume.** If you're hitting the same domain hard, the block is probably your traffic pattern, not the IP.

4. **Contact support.** If the same URL `403`s consistently, the domain may need a custom plugin. The [help center](https://scrapeunblocker.com/contact) is the right place.

<Warning>
  `403` is never an auth problem. Invalid API keys return `401`. If you're seeing `401`, see [Authentication](/authentication).
</Warning>

## 503 - no capacity on our side

We had no API capacity for the request right now: every node was busy past the queue limit, or none was up (`No server is available to handle this request`), or the render path was unavailable (`Render unavailable.`). This is a problem on our side, not the target's - and it is not billed.

**Recovery:** wait and retry. Exponential backoff is appropriate:

```python
import time
import requests

def get_with_backoff(url, key, max_attempts=5):
    for i in range(max_attempts):
        r = requests.post(
            "https://api.scrapeunblocker.com/getPageSource",
            params={"url": url},
            headers={"x-scrapeunblocker-key": key},
            timeout=125,
        )
        if r.status_code not in (500, 502, 503):
            return r
        time.sleep(min(60, 2 ** i))
    return r
```

`500` (internal error) and `502` with an HTML body (our load balancer lost the node) are the same class - ours, free, retry with backoff.

## 523 - the target is unreachable

The target site answered nobody over any of our exits: it is down, or it refuses connections in bursts. This is not a bot block, and it is not billed.

**Recovery:** retry after a pause (tens of seconds to minutes). Rotating `proxy_country` rarely helps - the site itself is not answering.

## Dead URLs - `200` with `X-Origin-Status`

If the target says the page does not exist (`404` / `410`), or its origin returns its own `5xx` error page, you get a `200` with that page as the body (it can be empty) and an `X-Origin-Status` header carrying the target's status. We reached the site; the URL is dead. It is billed like any delivered page, and **retrying will not change it** - check the header and drop or fix the URL. A URL whose domain does not exist returns `400 Hostname cannot be resolved` (also billed). See [Errors](/errors#dead-urls-x-origin-status).

## 504 - timeout

The request reached its time cap: `Request timed out.` on `/getPageSource` (60 s, 90 s with `steps`), or the SERP / plugin time budget on `/serpApi` and the dedicated plugin endpoints. Usually the target is slow for this URL.

**Recovery:**

1. **Retry.** Transient network issues account for most `504`s.
2. **Pick a different `proxy_country`.** Some country pools are slower or under heavier rotation.
3. **On `/serpApi`, lower `pages_to_check`.** Each additional page extends the time needed.

A `504` with an HTML body comes from our load balancer - that one is on our side. If `504`s hit many different domains at once, treat it like a `503`.

## 408 - browser timeout

Only returned by `/getImage`. Means the real-browser navigation took too long.

**Recovery:** retry. If persistent, the image URL may not point to something the browser can resolve - confirm the URL works in a regular browser first.

## 422 - validation error

You sent a bad parameter. The response body pinpoints the field:

```json
{
  "detail": [
    {
      "loc": ["query", "url"],
      "msg": "field required",
      "type": "value_error.missing"
    }
  ]
}
```

**Recovery:** fix the request. `422` is not retryable - retrying the same bad request will fail the same way.

## Retry policy that works

For most production workloads, this policy handles these error classes correctly:

```python
import time
import requests

RETRYABLE = {408, 500, 502, 503, 504, 523}

def scrape(url, key, max_attempts=4):
    last = None
    for attempt in range(max_attempts):
        r = requests.post(
            "https://api.scrapeunblocker.com/getPageSource",
            params={"url": url},
            headers={"x-scrapeunblocker-key": key},
            timeout=125,
        )
        if r.status_code == 200:
            return r
        last = r
        if r.status_code == 403 and attempt == 0:
            # one shot at rotating country
            r = requests.post(
                "https://api.scrapeunblocker.com/getPageSource",
                params={"url": url, "proxy_country": "us"},
                headers={"x-scrapeunblocker-key": key},
                timeout=125,
            )
            if r.status_code == 200:
                return r
            last = r
        if r.status_code in RETRYABLE:
            time.sleep(2 ** attempt)
            continue
        break
    last.raise_for_status()
```

This:

- Retries `408`/`500`/`502`/`503`/`504`/`523` with exponential backoff (failed calls are free).
- Tries one country rotation on `403`.
- Fails fast on `401`, `422`, and other terminal errors.

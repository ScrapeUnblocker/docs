title: "Parsed data extraction"
description: "Get structured JSON instead of raw HTML. Extraction uses Schema.org, __NEXT_DATA__, or AI-generated rules."
---

For most scraping workloads you don't want raw HTML - you want clean JSON with the fields that matter. Pass `parsed_data=true` to `/getPageSource` and ScrapeUnblocker extracts structured data using the best available method for that page.

## Request

<CodeGroup>

```bash cURL
curl -X POST "https://api.scrapeunblocker.com/getPageSource?url=https://www.amazon.com/dp/B08N5WRWNW&parsed_data=true" \
  -H "x-scrapeunblocker-key: YOUR_API_KEY"
```

```python Python
import requests

r = requests.post(
    "https://api.scrapeunblocker.com/getPageSource",
    params={
        "url": "https://www.amazon.com/dp/B08N5WRWNW",
        "parsed_data": True,
    },
    headers={"x-scrapeunblocker-key": "YOUR_API_KEY"},
    timeout=120,
)
payload = r.json()
```

```javascript Node.js
const res = await fetch(
  "https://api.scrapeunblocker.com/getPageSource?url=https://www.amazon.com/dp/B08N5WRWNW&parsed_data=true",
  {
    method: "POST",
    headers: { "x-scrapeunblocker-key": "YOUR_API_KEY" },
  }
);
const payload = await res.json();
```

</CodeGroup>

## Response shape

```json
{
  "data": {
    "page_type": "listing_detail",
    "data": {
      "title": "Volvo XC90 2.0 D5 Inscription AWD",
      "price": { "value": 31250, "currency": "EUR" },
      "brand": "Volvo",
      "model": "XC90",
      "mileage": "79,748 km",
      "power": "173 kW (235 hp)",
      "fuel_type": "Diesel",
      "transmission": "Automatic",
      "first_registration": "09/2018",
      "images": ["https://img.example.com/1.jpg", "https://img.example.com/2.jpg"],
      "specifications": {
        "Mileage": "79,748 km",
        "Power": "173 kW (235 hp)",
        "First Registration": "09/2018",
        "Trailer load braked": "2,700 kg"
      }
    }
  }
}
```

### `page_type`

Detected category of the page:

- `product_detail` - a single product (also films, books, apps)
- `listing_detail` - a single classified listing: vehicle, property, job, event, place
- `recipe_detail` - a recipe
- `article_detail` - a news story, blog post or wiki article
- `search_list` - search results or a listing grid
- `article_list` - a list of articles or posts (news front page, forum)
- `category_index` - a category navigation page
- `homepage` - a site's home page
- `review_list` - a page of reviews (Trustpilot, G2, Yelp, ...)
- `social_profile` / `social_post` - a creator or brand profile, a single post
- `not_found` - the target answered `404` / `410` (see below)
- `unknown` - the page could not be classified

### `data`

The extracted fields. Field names are English `snake_case` whatever the language of the page, and every price is normalized to `{ "value": <number>, "currency": "<code>" }`.

**List pages** (`search_list`, `article_list`, ...) return the results as `items`, plus `total` and `next_page` (the URL of the next results page, or `null` on the last one).

**Detail pages** (`*_detail`) return the item's fields at the top level, filled from the page's own spec table, its labelled values and the Schema.org data it publishes (price, brand, rating, mileage, ingredients, salary, ...). Next to them:

| Key | When present | What it holds |
|-----|--------------|---------------|
| `images` | the page has a photo gallery | image URLs, main image first |
| `features` | the page lists equipment / amenities | labels such as `"Heated seats"` |
| `specifications` | the page has a spec sheet | every row of it as `"label": "value"`, exactly as the page prints it (original language, values not normalized) |
| `reviews` | the page publishes reviews as Schema.org data | up to 10 reviews: `author`, `rating`, `date`, `title`, `text` |
| `content` | `article_detail` | the article's main text, paragraphs separated by blank lines |

Use the top-level fields for values you read across many sites; use `specifications` when you need a row the page shows that has no top-level field.

## When nothing can be extracted

If the page exists and renders (a call without `parsed_data` would return `200` with its HTML) but no structured data can be extracted from it, the answer is still **`200`**. The body keeps the usual `data` envelope with an empty `data`, says that nothing was extracted, and carries the rendered HTML so you can parse it yourself:

```json
{
  "data": {
    "page_type": "unknown",
    "data": {}
  },
  "data_extracted": false,
  "detail": "The page was rendered, but no structured data could be extracted from it. The rendered HTML is in `html`.",
  "html": "<html>\n <head>\n  <title>\n   Example Domain\n  </title>\n ..."
}
```

Check `data_extracted` (present only in this case) or an empty `data.data`. The call is billed like a call without `parsed_data`, since you receive the same page. Retrying returns the same result; if you expected data from this page, retry once with `refresh_rules=true` and a `rules_hint`.

A dead URL is different: when the target itself answers `404` / `410`, you get that status with `{"data": {"page_type": "not_found", "data": {}}}` - see [Dead URLs](/errors#dead-urls-x-origin-status).

## When parsed data is the right choice

<Check>**Use it when** you're scraping a known page type at scale - products, listings, articles, recipes, jobs. Saves you from writing per-site parsers.</Check>
<Warning>**Skip it when** you need a field the extractor doesn't expose, or when you need raw HTML for downstream tooling. Fetch the HTML and parse it yourself instead.</Warning>

## Combining with `get_cookies`

You can set both `parsed_data=true` and `get_cookies=true` on the same request. The response gains a `cookies` field and a `proxy` field alongside `data`:

```json
{
  "data": { "page_type": "product", "data": { ... } },
  "cookies": [ { "name": "session", "value": "...", "domain": "..." } ],
  "proxy": "us"
}
```

See [cookies and sessions](/guides/cookies-and-sessions).
